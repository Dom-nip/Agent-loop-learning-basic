# Loop 工程实战册：从 ReAct 到 Harness

> 主册（chapters/book.md，另有特别篇收录 OpenAI/Anthropic 工程文献）论述**为什么**——每项技术的历史脉络与淘汰逻辑；
> 本册演示**如何实现**——12 个完全独立、可交互运行的真实 agent 项目，
> 完整走一遍从 300 行 ReAct 脚本到七层 harness 的工程演进。
>
> 建议与主册配合使用：在主册读到某一机制"为什么如此设计"时，转入本册对应 stage 观察其实现；
> 实现受阻时，回主册检索原理。

---

## 引言：从"90 行脚本"到 harness 的工程距离

任何熟悉 OpenAI API 的开发者都能在半小时内写出一个 agent：

```python
while True:
    reply = llm(messages)
    if 需要工具: 执行工具; 将结果写回 messages
    else: break
```

这段脚本在演示场景中表现良好，在真实任务中却难以存活：缺乏循环控制时，它会在第 40 轮
原地循环直至耗尽预算；缺乏护栏时，网页中的一句"忽略之前的指令"即可使其失效；
缺乏持久化时，崩溃后必须从零开始；缺乏可观测性时，故障排查无从下手。
**从 90 行脚本到 harness 的距离，不是一个框架，而是十余次真实失败
各自换来的一个机制。**

本册把这十几个机制拆成 12 个 stage，按四幕排布：**可运行 → 可控 →
可靠 → 可扩展**。每个 stage 是一个独立完整的项目（依赖 `openai` +
仓库根目录的 `config.py`，12 个 stage 共用一份；stage11 另需 `PyYAML`），
有完整的阶段教程、可交互的入口、示例会话。
可以从任意一个 stage 开始；但按顺序完整走一遍，可以逐一观察每个机制
如何由前一机制的失败直接催生。

**运行方法：**

```bash
cd loop-engineering/stage01_react_text_protocol   # 任选一个 stage
pip install -r requirements.txt
# 填仓库根目录 config.py 三行（API_KEY / BASE_URL / MODEL，全部 stage 通用）
python src/main.py                                 # 进入交互式对话
```

每个 stage 文件夹内：`README.md`（阶段教程：目标/原理/运行方式/观察点/
设计权衡/竞争方案淘汰原因）、`src/`（全部源码，中文注释）、`workspace/`
（agent 的沙盒）、`examples/transcript.md`（一段真实运行记录）。

**退出方式**：12 个 stage 的交互入口均设有受控退出。11 个对话式
stage（01–10、12）输入 `/exit` 或按 `Ctrl+C` / `Ctrl+D` 均可优雅退出；
stage11 为菜单式评测界面，输入 `q` 退出。退出并非裸 `break`，各 stage
在退出路径上挂载了收尾逻辑：stage04、12 触发长期记忆沉淀（stage04 连
`Ctrl+C` 也会被映射为 `/exit`，保证沉淀必定执行）、stage03 退出前打印
上下文分区报告、stage08 落盘轨迹文件并提示回放命令、stage09 提示
未完成检查点（重启可续跑）、stage10 经 `finally` 优雅关闭 MCP server，
其余 stage 打印会话统计（轮次 / 工具调用 / schema 修复次数）。会话内的
子提示同样对中断安全：危险操作确认门（stage06/07/12）在 `Ctrl+C` / `Ctrl+D`
时视为"拒绝"，stage02 `/mode` 与 stage03 `/load` 的参数输入视为"取消"，
不会以未捕获异常中断。

**与主册的章节对应**：每个 stage 的 README 开头都标了"正文章节锚点"，
例如 stage01 ↔ 第 02/04 章。主册与实战册互为索引。

## 第一幕 · 可运行（stage01-03）：先建立最小循环，再优化运行质量

### 时代背景

2022-2023 年。ReAct 论文发表后，实践者们发现"边想边做"这一朴素结构
竟然有效。第一代实践者的全部精力集中于让循环运行起来；
随即发现："能够运行"与"运行良好"之间，相隔三道门槛。

### stage01 · ReAct 文本协议 —— 循环的起点

**遇到的问题**：LLM 只能生成文本，如何使其"调用"一个 Python 函数？
2022 年的答案是：把工具说明书写进 prompt，让模型按格式输出
`Thought / Action / Action Input`，harness 用正则解析后执行，把结果作为
`Observation` 喂回去。推理与行动由此交织——**行动的价值不在于"做了"，
而在于"做了之后世界给你反馈"**：纯 CoT 无论推理多完善都缺乏事实校验，
AutoGPT 式先规划后执行则计划与现实脱钩后无从修正，两者皆败于"每步都看一眼
现实"的 ReAct。

**本 stage 的设计决策**：协议即 system prompt；解析失败不崩溃而是将规则
重述一遍（repair loop——文本协议时代最重要的工程发明）；一切工具结果
（包括错误）都是 Observation 字符串；`max_turns` 自第一天即存在。
同时也可观察到文本协议的税：JSON 转义依赖模型自觉、格式随轮数漂移、
每轮重发协议的 token 开销。

**同时期被淘汰的方案**：纯 CoT（无行动验证）、AutoGPT 式预规划、
Toolformer 式微调内化（成本过高，被通用模型接口取代）。详见
`stage01_react_text_protocol/README.md`（教程锚点：第 02、04 章）。

### stage02 · Function Calling —— 协议下沉为基础设施

**遇到的问题**：各团队都在为自己的 ReAct 解析器叠加补丁：容错正则、
few-shot 修复示例、格式重试上限……2023 年 6 月 OpenAI 发布 Function
Calling，终结了这场补丁式适配的竞赛：工具说明书变成 API 的 `tools` 参数
（JSON Schema），模型返回结构化 `tool_calls`——**在 API 层能解决的
问题，不该在 prompt 层修**。协议税没有全免：参数值仍可能不合 schema，
于是 repair loop 进化成"校验失败 → 错误当 tool result 喂回 → 模型自己改"。
新能力也随之而来：并行工具调用（一条消息多个 tool_calls，轮次减半）。

**同时期被淘汰的方案**：文本协议 patch 库（旋即过时）、纯 JSON mode
（保证合法 JSON 但不保证"哪个工具的合法参数"）。详见
`stage02_function_calling/README.md`（锚点：第 03 章）。

### stage03 · 上下文工程 —— 真正的胜负手

**遇到的问题**：协议稳定后，agent 仍会随运行逐渐劣化、成本持续攀升。
原因在上下文：窗口是注意力预算而非内存——填充越满注意力越稀薄（Context Rot），
一次 `cat` 大文件即可消耗 3 万 token，长循环后早期指令"失忆"。

**本 stage 的解法是四件事**：token 记账（掌握消耗分布）、工具结果截断
（源头截断——污染不进入账本）、三分区（宪法/文档/历史——顺序稳定以保全
prompt cache）、阈值压缩（早期消息由 LLM 摘要并入文档区）。压缩的切分点必须
是 user 消息——否则 tool 消息与其引用的 tool_calls 被拆开，API 直接返回
400 错误；此类细节即上下文工程的日常。

**同时期被淘汰的方案**："窗口够大即胜"的长窗口全量注入路线（Context Rot
实验证伪）、每次全量重建（cache 命中率归零，成本 ×10）、朴素滑动窗口
（丢弃的恰是最重要的任务目标）。详见 `stage03_context_engineering/`
（锚点：第 10-12 章）。

## 第二幕 · 可控（stage04-06）：从可运行到可持续运行

### 时代背景

2024 年。单会话 demo 已随处可见，问题转为：如何使其跨会话记忆、
如何以分工完成大型任务、如何保证其终止。AutoGPT 失败的教训尚新，
每一条都值得转化为一个机制。

### stage04 · 记忆与文件系统 —— 外置记忆

**遇到的问题**：会话结束即状态归零，用户每次都需重新提供背景信息。
2023 年的主流答案是将一切存入向量库（AutoGPT 历史遗留影响），结果是时序错乱、
新旧混杂、检索出半相关文本。**语义检索管知识召回，路径寻址管状态存取**
——"我知道状态在哪"永远比"我猜相关的在哪"可靠。

**本 stage 的解法**：三层记忆各就各位——会话历史（窗口内）、工作笔记
（notes/，由 agent 以文件工具自行管理）、长期记忆（memory/MEMORY.md +
sessions/ 归档）。启动注入、收尾沉淀（由 LLM 筛选"值得跨会话记住的"内容）、
显式 save_memory 工具、/forget 遗忘机制。

**同时期被淘汰的方案**：向量库存任务状态（时序错乱）、无记忆从零开始
（体验严重受损）、托管记忆服务（教学场景过度基建——文件系统是记忆的
最简可行方案）。详见 `stage04_memory_filesystem/`（锚点：第 13 章）。

### stage05 · Subagent —— 上下文的空间减法

**遇到的问题**：读取大文件、逐项分析等高消耗操作全部在主对话内完成时，
上下文迅速膨胀。多 agent 共享全上下文（"AI 软件公司"）的教训近在眼前：
每个成员携带全量历史，任一环节出错即逐级放大。

**本 stage 的解法**：分叉-回收。主代理将独立子任务打包（任务包五要素：
目标/最小上下文/工具集/边界/输出格式——写进 spawn 工具的 schema，
接口合同代替口头纪律），并行分派给从零开始的子代理；子代理的中间过程
随实例消亡，只有报告回流，由主代理合成。预算护栏：一次最多 4 个。

**同时期被淘汰的方案**：常驻多 agent 群聊（上下文膨胀+传递损耗）、
串行流水线（实现了隔离但不并行）、单 agent 承载全部工作（小规模场景下
它反而最简单——subagent 的引入必须服务于隔离需求）。
详见 `stage05_subagent/`（锚点：第 07、15、16 章）。

### stage06 · 循环控制 —— "保证它停"

**遇到的问题**：AutoGPT 的三大败因均属控制问题：无界循环耗尽预算、
无人干预时偏离且无人纠正、原地循环数小时。system prompt 中写"你该停就停"
是软约束——stage05 中模型连"≥2 个子任务才分派"的纪律都会违反。

**本 stage 的解法是四道显式机制，全部代码可达**：硬上限（轮数 + token
预算，检查在调用前）、危险操作确认门（拒绝作为工具结果喂回，模型得以
改道而非空转）、stall 检测（连续重复动作 → 提醒 → 强制重写计划）、短计划
（≤5 步、随观察修订——计划是"消耗品"而非"宪法"）。

**同时期被淘汰的方案**：无界循环且不作干预（Continuous Mode）、完全固定
流程（那是 workflow 不是 agent）、依赖模型自省停止（长循环中模型会忘记
承诺）。详见 `stage06_loop_control/`（锚点：第 04、09、21 章）。

## 第三幕 · 可靠（stage07-09）：安全性与长期可靠性

### 时代背景

2024-2025 年。agent 开始实际投入生产，攻击面与可靠性问题随之而来：
提示注入从学术演示演变为真实事故，长任务崩溃的期望损失以小时计。
"可靠"从加分项变为及格线。

### stage07 · 护栏与安全 —— 防御必须在工具层

**遇到的问题**："请你不要被注入"防不住任何东西——注入内容与 system
prompt 走同一通道、同一格式，模型在长上下文中无法分辨信源。

**本 stage 的解法是四道代码可达的防线**：数据通道清洗（工具结果包
`<data>` 标记 + 注入模式就地标注）、三态权限（allow/ask/deny，
permissions.json 可配置）、命令黑名单（run_python 先经黑名单扫描再执行）、
审计日志（JSONL append-only，事故可回放）。以一段内嵌 5 类注入模式的
"邮件"做真实攻击演练——防御不依赖模型自觉：即使模型被骗，deny 的工具
依然无法进入、ask 的操作依然需确认。

**同时期被淘汰的方案**：提示层防御（结构性缺陷：同通道无可信度）、
事后输出过滤（工具已执行完毕，过滤的是"宣布"而非"行为"）、不加区分
全部 deny（安全但功能性降级为聊天机器人）。详见 `stage07_guardrails_security/`
（锚点：第 23 章）。

### stage08 · 可观测性 —— 故障定位不依赖猜测

**遇到的问题**：print 调试信息转瞬即逝；仅检查 final answer——正确
可能出于偶然，错误则无从定位。故障恢复的第一步是定位，定位需要轨迹。

**本 stage 的解法**：Span 轨迹树（task → llm → tool 父子成树，谁干的/
父任务/耗时/token/成本/成败）、JSONL 实时逐条落盘（异常也落盘——已落盘的
崩溃 span 远比丢失的有价值）、离线回放（`--replay` 跨进程重建现场）、成本
计量（token × 单价表）。可以观察到成本的结构：输入 token 通常是输出的
5-10 倍——stage03 的压缩省钱逻辑在此获得账本印证。

**同时期被淘汰的方案**：print 调试、只看 final answer、全量托管观测
平台（内网与教学场景先以本地 JSONL 打底）。详见 `stage08_observability/`
（锚点：第 22、24 章）。

### stage09 · 长时任务 —— 持久化的对象是状态而非进程

**遇到的问题**：运行 2 小时的任务在第 90 轮崩溃即全部作废；serverless
15 分钟超时对长任务构成硬性终止。

**本 stage 的解法**：**持久化执行的单位不是进程，是状态**。每轮落检查点
（历史即状态，append-only 序列化即存盘；原子写防残缺）、崩溃后重启续跑
（至多损失一轮而非全部进度）、异步任务队列（submit 立即返回、poll 查进度、
完成写结果文件）、取消传播（协作式：当前步完成后生效——不中断进行中的
写入）。

**同时期被淘汰的方案**：同步阻塞脚本（崩溃期望损失 50%）、serverless
直接部署（超时强制终止）、崩溃后自动重启整个任务（重复消耗预算）。详见
`stage09_long_running/`（锚点：第 20、25 章）。

## 第四幕 · 可扩展（stage10-12）：从单一系统到能力生态

### 时代背景

2025-2026 年。单 agent 的工程要素已经齐备，扩张的瓶颈转移至能力生态：
知识规模超出 prompt 容量，工具数量超出宿主集成能力。同时，"改动之后
是否变好"不能再凭主观感受回答。

### stage10 · Skill 与 MCP —— 两个行业标准

**遇到的问题一（知识）**：领域知识全部置入 prompt，成本高且互相干扰——
写周报时清洗规则在场，模型冒出"先探查再动手"的话术。**解法**：Agent
Skills 三层渐进披露——元数据常驻（~50 token/技能）、正文经 load_skill
按需加载、参考文件更深一层按需读取。技能库达 30+ 时，与全量注入的差距
在 100 倍以上，尚未计入干扰消除的收益。

**遇到的问题二（工具）**：M 个宿主 × N 个工具的私有集成（M×N 困境），
工具与宿主紧耦合。**解法**：MCP（Model Context Protocol）将 N 降至 1
（工具方实现一次 server）、M 降至 1（宿主实现一次 client）。本 stage
用 300 行实现最小 stdio client/server（initialize / tools/list /
tools/call），桥接后模型完全无感——这就是"基础设施"的定义。

**同时期被淘汰的方案**：全量注入 prompt、以 RAG 存放程序性知识（整体
使用的知识被切片割裂）、M×N 私有集成。详见 `stage10_skill_mcp/`
（锚点：第 14、17 章）。

### stage11 · 评测 harness —— 质量先于智能

**遇到的问题**："修改 prompt 而不运行回归"等价于全局变量失控——
上一版本可用而当前版本失效。demo 驱动开发、单例目测、主观判断，
本质都是把上线过程当作回归测试。

**本 stage 的解法**：YAML 用例集（程序判据 contains/not_contains/regex

+ LLM 裁判 rubric 双轨）、双版本回归对比（v1 基线 vs v2 迭代版，逐用例
  标 ↑修复/↓退化）、`--gate` CI 门槛（通过率不达标退出码 1）。实测中
  v1 收到"写一首诗"请求时确实输出了一首购物诗（角色漂移，程序判据处于
  边界、裁判 0 分判定），v2 依靠行为规则修复——**评测驱动开发不是方法论
  口号，而是把"变好"变成可验证事实的机器**。

**同时期被淘汰的方案**：demo 驱动、单例目测、纯人工全量评审（吞吐
不足且不可重复——其正确位置是抽检校准裁判）。详见 `stage11_eval_harness/`
（锚点：第 08、22 章）。

### stage12 · 完整 harness —— 七层收官

**遇到的问题**：全部组件均已就绪，如何组装为一个可维护的系统？

**本 stage 的答案**：七层架构——L1 能力（llm）/ L2 上下文（分区截断
压缩）/ L3 工具（干净实现）/ L4 护栏（清洗权限黑名单审计）/ L5 控制
（硬上限确认门 stall）/ L6 观测（span 成本回放）/ L7 记忆（长期记忆
会话沉淀）。层间只传数据、互不知情，编排集中在 agent.py；防御优先级
固定（deny > 黑名单 > 确认 > 清洗）；观测与记忆是旁路（可整体拆卸）。
实测一次注入攻击：四层在一秒内接力完成检测、标注、审计、拒执，
全程 6 个 span、¥0.0036。

**同时期被淘汰的方案**：重框架式继承链（分层 ≠ 抽象堆叠）、单文件
巨型脚本、微服务式进程拆分（先在进程内做对分层）。详见
`stage12_full_harness/`（锚点：第 21 章）。

## 附录 A · 主决策树：是否应使用 Agent

> 由主册第 27 章浓缩而来（该章已并入本册）。逐项核对以下决策树：
> 任何一问判定为否定，都不应强行采用 agent。

```
Q1 任务的"下一步做什么"能预先写成固定流程吗?
 ├─ 能 ──► 用 workflow（链式/路由/并行，主册第 9 章）。这不是妥协，
 │          是对可靠性和成本的尊重。
 └─ 不能（路径取决于中间结果）
      Q2 有办法验证结果对错吗？（测试/判分/溯源/人工抽查）
       ├─ 没有 ──► 停止。先建立验证手段（主册第 22 章）。
       │            没有 ground truth 的场景是 Agent 的禁区。
       └─ 有
            Q3 单次 LLM 调用能解决吗?
             ├─ 能 ──► 一次调用。不为演示复杂度付费。
             └─ 不能
                  Q4 需要工具+多轮循环吗?
                   ├─ 不需要，只是多步文本 ──► 链式 workflow + 检查门
                   └─ 需要
                        Q5 预算/延迟承受多少轮?
                         ├─ 很少（≤5 轮）──► 小 loop + 低档模型
                         └─ 充足 ──► 采用 agent loop，必配三项机制：
                                     ① max_turns/预算硬上限（stage06）
                                     ② 高危动作人工确认（stage06/07）
                                     ③ evals 先于迭代（stage11）
```

三个高频分支的补充说明：

- **Q2 没有验证手段怎么办？** 两条出路：将任务改造为可验证的（先建
  ground truth：评测集、判分器、可检查的产物格式——stage11 即起点）；
  或退回 workflow + 人工终审。**跳过验证直接运行自主循环**是 2023 年最大
  教训的当代复现。
- **Q5 预算充足也不应一次给满**：从 5 轮开始评测校准，逐步放宽——
  自主性的扩张必须有 evals 背书。
- **走完整棵树仍属"workflow 即可解决却坚持使用 agent"时**：agent 是
  处理开放性问题的最后手段，而非默认选项。

### 上线前自查清单（七个维度）

**上下文**：宪法式系统提示是否完整？工具输出是否源头治理？长任务有压缩/外置方案？
常驻知识最小化（Skills）？
**护栏**：硬停止（轮数/预算）？高危操作确认门？错误反馈路径畅通？
**结构**：workflow/agent 判定已执行？高消耗任务已由 subagent 隔离？顺序主线未被破坏？
**生态**：工具是否经 MCP 暴露？第三方 server 已审查？轨迹落盘可查？
**评测**：案例库 ≥20 且来自真实失败？程序判据优先？裁判异族+清单
rubric？变更必跑回归？
**安全**：危险命令白/黑名单？注入防线（结果当数据）？最小权限？
**可靠性**：重试幂等？限流与降级？可观测三支柱（日志/指标/追踪）？

### 一些通用方法

1. 下一步由谁决定？→ 代码=workflow / 模型=agent（能不用则不用）
2. 未建立判分器不启动；案例库是第一资产
3. 系统提示=失败模式封堵清单；工具描述注明"何时不用"
4. 窗口是注意力而非内存；源头截断>清除>压缩>外置
5. max_turns+预算+确认；短计划随观察修订
6. 高消耗任务外包 subagent（任务包五要素）；顺序主线不拆
7. 工具=MCP；知识=Skills；事实=RAG；流程=Skill；能力=模型
8. 结果=数据≠指令；最小权限；高危必确认
9. 幂等+退避+限流；降级有预案；日志/指标/追踪齐备
10. 程序判据>LLM裁判>人工；改任何"全局变量"必跑回归
11. 全自动收敛到异步小任务；人在环是成本最低的错误恢复
12. 智能补丁终被内化；环境管理（上下文/护栏/评测）是长期阵地
