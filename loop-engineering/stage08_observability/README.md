# stage08 · 可观测性 —— 轨迹树、计时、成本与回放

> 第三幕 · 可靠（2/3）。故障发生时，print 调试无法提供答案："模型为什么
> 这么做？哪一轮开始跑偏？成本消耗在哪里？"本 stage 为循环装上仪表：
> Span 轨迹树、span 计时、token/成本计量、JSONL 结构化日志、离线回放。

## 1. 本阶段目标

**使每一次循环都留下可回放的结构化轨迹**：task → llm → tool 三级 span 父子
成树，每个 span 记录 执行者 / 父任务 / 耗时 / token 估算 / 成本 / 成败；
实时落 JSONL，退出后可跨进程回放复盘。

## 3. 原理与设计决策

**观测为什么是"可靠"的一部分？** 故障恢复的第一步是定位。没有轨迹的
agent 出现问题后只能依赖推测：重跑（成本高昂）、添加 print（修改代码并
重启）。有轨迹的系统：`--replay` 打开 JSONL，跑偏的那一轮、高成本的那个
工具、报错的那个调用直接看树。

**本 stage 的关键实现决策（`trace.py`）：**

1. **Span = 有名字的工作**：kind（task/llm/tool）+ name + 父子关系 +
   计时 + token 估算 + 成本 + 状态。上下文管理器保证异常也会落盘
   （`__exit__` 里标记 error——崩溃的 span 比消失的 span 有用得多）。
2. **父子成树而非平铺列表**：`task_span → llm_span → tool_span` 的嵌套
   让"这一轮为什么慢"可以下钻（是 LLM 耗时长，还是工具耗时长）。
3. **JSONL 逐条实时落盘**：append-only、每行一个 span、进程崩溃也不丢
   已完成的记录。这是结构化日志的最小形态（第 24 章三支柱的日志+追踪）。
4. **成本计量**：输入 token 按请求消息估算、输出按回复估算，乘以 PRICE 表
   （示例单价，按服务商实价修改）。粗粒度但数量级正确——足以回答
   "该任务的成本构成"这类问题。
5. **回放是一等公民**：`main.py --replay logs/trace-xxx.jsonl` 用同一套
   渲染逻辑离线重建树——观测数据的价值在"事后"。
6. **插桩在 agent 层，工具保持干净**：与 stage07 相同的分离原则——
   `InstrumentedAgent` 包裹一切，`tools.py` 不知情。

## 5. 观察点

- **树形下钻**：哪个任务最慢？展开看是 llm span 长还是 tool span 长——
  前者优化提示长度，后者优化工具实现。
- **成本结构**：输入 token 通常是输出的 5-10 倍（历史越来越长）——这正是
  stage03 上下文工程直接降低成本的原因，账本在此互相印证。
- **错误 span**：构造一个读取不存在文件的任务，观察轨迹树中的错误标记
  与错误信息——排查从"回忆"变成"检索"。
- **回放一致性**：退出重进用 --replay，树应与退出时一致——日志即真相。
- **PRICE 表的杠杆**：把输入单价 ×10，/cost 立即反映——成本可见性是
  成本治理（正文第 26 章）的前提。

## 6. 设计权衡

| 优势 | 代价 |
|---|---|
| 200 行内实现追踪+日志+成本，零依赖 | span 粒度手工挑选（没有自动埋点生态） |
| 异常也落盘，崩溃现场可回放 | token 是估算值（成本精度 ±30%） |
| JSONL 通用格式：任何工具都能读 | 无采样/限流，高吞吐下日志量会失控 |
| 回放与实时共用一套渲染 | 无跨进程 trace 串联（真分布式需 OpenTelemetry） |

## 7. 同期竞争方案的淘汰原因

- **print 调试**：开发阶段便捷，生产阶段失效——信息一闪而过、没有结构、
  无法检索、无法跨进程。其合理遗产是 verbose 模式（本 stage 保留）。
- **只看 final answer**：把 agent 当黑盒评测。final answer 正确 ≠ 过程正确
  （可能出于偶然），final answer 错误 ≠ 无从下手（轨迹能定位在哪一轮
  发生偏离）。第 22 章的"看轨迹"正是评测驱动开发的第二条观察路径。
- **全量托管观测平台**（LangSmith/LangFuse 类）：能力完整（采样、数据集
  关联、团队协作），但引入外部依赖与数据出域问题。教学与内网环境可先以
  本地 JSONL 为基础，规模扩大后再接入平台——格式同源（均为 span 流），
  迁移成本低。

## 8. 与下一个 stage 的衔接

可观测性解决了"看得见"，但长任务还有"存活"的问题：运行 2 小时的任务
崩溃在第 90 轮，进程重启后能否续跑？能否避免重复消耗？stage09
（long_running）为循环加入检查点与恢复、异步任务队列、取消传播。
