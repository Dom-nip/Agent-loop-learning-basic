# stage05 · Subagent —— 分派、并行隔离与 fan-in 合成

> 第二幕 · 可控（2/3）。上下文的**空间减法**：将噪声密集的中间处理外包给
> 从零初始化的子代理，主对话仅回收最终报告——被隔离的不是"人"，而是上下文。

## 1. 本阶段目标

**以 spawn_subagents 实现上下文隔离**：主代理（Lead）把可分解的独立子任务打包
（任务包五要素），并行分派给多个干净上下文的子代理（SubAgent）；子代理的中间
过程随实例消亡，只有最终报告回流主对话，由主代理合成（fan-in synthesis）。

## 3. 原理与设计决策

**为什么隔离优于共享上下文？** 多 agent 共享全部对话历史的问题（第 7 章
"传话游戏"实验）：每个成员都携带全量历史，上下文成倍膨胀，关键指令被稀释，
一处失真逐级放大。subagent 的答案是**分叉-回收**：分叉出去的实例从零开始
（只有任务包），回收回来的只有结论。主对话的上下文增长 = 任务包 + 报告，
与子任务的复杂度无关。

**本 stage 的关键实现决策：**

1. **任务包五要素写进 spawn 工具的 schema**（`tools.py`）：goal / context /
   tools / boundaries / output_format 是 required 字段——**接口合同代替口头
   纪律**。信息不完整的任务包无法通过 schema 校验（stage02 的 repair loop
   在此承担了"分派培训"的职能）。
2. **子代理的 system prompt 极短**（`subagent.py`）：身份 + 任务包内容 +
   边界重申。它不需要主代理的对话历史、不需要全量工具——**最小授权 =
   最小上下文**。
3. **真并行**（`run_parallel` 用 ThreadPoolExecutor）：LLM 调用是 IO 密集，
   线程池即可；OpenAI 客户端线程安全。三个子任务并行，墙钟时间 ≈ 最慢
   一个，而不是三个之和。
4. **预算护栏**：一次最多 4 个子代理（`_spawn` 里硬编码）。无预算约束的
   并行将导致成本失控（失败模式 #17）。
5. **fan-in 合成由主代理承担**：system prompt 明确"由你合成最终结论，不要
   原样转贴"——合成分歧、对比差异、指出冲突，这是 Lead 的价值所在。
6. **子代理工具白名单**：任务包里 tools 字段只点名的才装配。子代理调用了
   未授权工具会收到明确拒绝——最小权限从默认开始。

## 4. 运行方式

```bash
cd loop-engineering/stage05_subagent
pip install -r requirements.txt
# 填仓库根目录 config.py 三行后：
python src/main.py
```

演示路径：

```
你> /flooddata          # 生成三个门店的销售 CSV（各 120 行）
你> 对比三个门店的销售情况，给出综合结论
┌─ 任务：对比三个门店的销售情况，给出综合结论
│ [turn 1] 🔧 spawn_subagents(3 个任务包：store_a/b/c 各一份)
│      [东区店 t1] 🔧 run_python
│      [南区店 t1] 🔧 run_python      ← 真并行，同时执行
│      [西区店 t1] 🔧 run_python
│           →（三份报告回流）
│ [turn 2] 💬（合成）
└─ ✅ Final Answer: 三店对比……东区店销售效率最高……
```

完整示例见 `examples/transcript.md`。

## 5. 观察点

- **任务包质量**：分派两个不同任务，比较子代理报告质量与任务包完整度的
  关系。context 表述含糊时，子代理将"自由发挥"——隔离会放大任务包缺陷。
- **主上下文的增量**：`/stats` 前后对比。三个 120 行文件的分析，主对话只
  增加三段报告（几百 token），而不是三个文件全文（几万 token）。
- **并行度**：三份子报告出现的时间戳几乎同时（真并行），而非排队。
- **合成 vs 转贴**：能力较强的模型会主动对比三店差异并给出结论；较弱的
  模型将三段报告拼接在一起——合成能力是 Lead 的分水岭。
- **越权测试**：任务包 tools 只给 read_file，检验子代理请求 run_python 时
  是否被拒绝。

## 6. 设计权衡

| 优势 | 代价 |
|---|---|
| 主上下文增量恒定，与子任务复杂度解耦 | 任务包质量不佳时，子代理会以高置信度产出错误结果（隔离悖论） |
| 真并行节省墙钟时间 | token 总量上升：每个子代理都要重读背景 |
| 失败隔离：子代理崩溃不污染主线 | 合成质量依赖 Lead 能力 |
| 子代理可独立降级用便宜模型 | 并发有账单放大效应，必须配预算护栏 |

## 7. 同期竞争方案的淘汰原因

- **共享全上下文的多 agent 群聊**（2023 年"AI 软件公司"MetaGPT 式常驻角色）：
  产品经理、架构师、程序员各自常驻、共享对话。失败源于上下文膨胀（每个
  角色都携带全量历史）与传递损耗（一处丢失，逐级放大）。最终留存下来的
  正是 orchestrator-worker 的分叉-回收原语。
- **串行流水线**（A 的输出作为 B 的输入依次传递）：隔离做到了，但没有并行，
  且传递链越长衰减越重。并行分派 + Lead 合成把"链"改造成"扇出-扇入"。
- **单 agent 承载全部工作**：把所有文件读进一个上下文内逐一分析。上下文小的时候
  它反而最简单可靠——所以判据是"可分解的独立子任务 ≥2"才分派。
  subagent 并非普适方案，而是特定场景的工具。

## 8. 与下一个 stage 的衔接

隔离与并行提升了 agent 的能力上限，也降低了其行为的可预测性：何时停止、
是否原地循环、危险操作由谁拦截？stage06 将"循环控制"实现为显式机制：
max_turns、token budget、人工确认门、stall 检测、短计划重写——从被动等待
停止，转为主动保证停止。
