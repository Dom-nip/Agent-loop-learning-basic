# stage11 · 评测 harness —— 程序判分、LLM 裁判、回归与门槛

> 第四幕 · 可扩展（2/3）。前十个 stage 的主题是"改"，本 stage 回答"改好了
> 没有"：缺乏评测体系的 agent 迭代，等同于无回归保护的代码变更——"上周
> 正常、本周失效"的问题无从定位（失败模式 #25）。本 stage 建立最小可用的质量
> 体系：YAML 用例集 → 程序判分 + LLM-as-judge → 版本回归对比 → CI 门槛。

## 1. 本阶段目标

**使 agent 的每次改动都有分数背书**：6 条用例（含程序判据与裁判 rubric）、
双版本回归对比（v1 基线 vs v2 迭代版）、`--gate` 命令行门槛（通过率不达标
退出码 1，可接 CI）。

## 3. 原理与设计决策

**被测系统（`targets.py`）**：一个电商客服 agent 的两个版本——
v1 只有知识库（基线），v2 在 v1 的失败模式上反推出行为规则（只依据知识库、
先答案后指引、数字原样引用、超范围引导转人工）。**v2 的规则并非主观拟定，
而是由评测失败反推得出的**——这正是评测驱动开发的实践路径。

**判分流水线（`runner.py`）：**

1. **程序判分优先**：`contains` / `not_contains` / `regex` 直接断言答案
   文本——低成本、零调用、100% 可复现。凡程序可判定的判据不应交由
   裁判模型（第 22 章铁律）。
2. **LLM-as-judge 管语义**：rubric 清单 + min_score，温度 0 + JSON 输出 +
   容错解析（截取首尾大括号）。裁判管的是"程序写不出的对"：是否承认
   无知、结构是否先答案后指引、有没有角色漂移。
3. **裁判故障与判分解耦**：裁判输出解析失败时该用例标记 judge_error 而非
   fail——评测基础设施的故障不应制造被测系统的假阴性。
4. **异族裁判**：`llm.py` 的 `judge_chat` 优先用 config.py 的 JUDGE_*
   三项（另一厂商的模型），未填则回落主配置。裁判与被测模型同源时会
   产生偏好偏差（失败模式 #26），生产环境务必使用异族裁判。
5. **结果落盘 + 对比函数**：每次跑完存 `results/<label>.json`；
   `compare()` 逐用例对比 A/B，标出 ↑修复 / ↓退化 / →持平。
6. **CI 门槛**（`run_eval.py --gate`）：通过率 < 阈值则退出码 1。
   评测的价值在闸门，不在报告。

## 4. 运行方式

```bash
cd loop-engineering/stage11_eval_harness
pip install -r requirements.txt        # openai + PyYAML
# 填仓库根目录 config.py 三行（可选：JUDGE_* 填另一厂商的异族裁判）
python src/main.py                     # 交互菜单
python src/run_eval.py --gate          # CI 门槛模式
```

## 5. 观察点

- **v1 的失败模式**：out-of-scope 用例上它输出了一首购物诗——知识全部
  正确也无济于事，行为约束缺失即表现为角色漂移。程序判据捕捉不到这类
  失败（"not_contains 退货政策"仅属偶然满足），裁判 rubric 才是主力。
- **程序判据的脆弱性**：refund-window 的 `contains "7"` 其实能被"17 天"
  满足——字符串断言是必要不充分条件，关键数字要配合裁判语义核对。
- **裁判的稳定性**：同一用例运行三遍，judge 分数应一致（温度 0 的意义）；
  若波动大，rubric 要写得更可判定（"第一句话直接给出核心答案"优于
  "回答要好"）。
- **门槛阈值的选择**：0.7 起步，随评测集成熟度上调。阈值太松形同虚设，
  太紧会阻塞正常迭代——门槛本身也要接受评测。
- **成本**：本套 6 用例全跑（含裁判）≈ 12 次调用。评测集扩到 50 条时，
  先以 `--no-judge` 作日常门禁，全量裁判评测置于发版前。

## 6. 设计权衡

| 优势 | 代价 |
|---|---|
| 双判分器互补：程序管确定性，裁判管语义 | 裁判有成本有延迟，且本身需校准 |
| 回归对比把"改坏"拦截在合并前 | 用例集维护是持续投入（6 条是演示，真实要 20+） |
| --gate 退出码可直接接 CI | 字符串判据会误伤（改写措辞就挂） |
| 全部本地文件，可进版本库 | 单轮问答评测；多轮任务评测需轨迹级判分（未实现） |

## 7. 同期竞争方案的淘汰原因

- **demo 驱动开发**（改动后手动验证）：速度最快，覆盖率最低——人工验证
  的路径往往恰好避开了缺陷。上线后的第一批真实流量将充当回归测试。
- **单例目测 + 直觉**："看了几个例子都挺好"。单例偏差（失败模式 #24）：
  通过率是分布，不能以直觉替代；不观察分布就发现不了"偶发性异常"。
- **纯人工评审**：质量最高，吞吐最低，且不可重复（同一答案两个人评
  结果不同）。正确位置是抽检与裁判校准，不是全量门禁。
- **只测最终答案不看轨迹**：答案正确可能出于偶然，答案错误可能仅源于
  单步偏差。本 stage 聚焦单轮判分；轨迹级评测（哪一步开始错）接 stage08
  的轨迹数据是进阶方向。
