# stage09 · 长时任务 —— 检查点恢复、异步队列与取消传播

> 第三幕 · 可靠（3/3）。前八个 stage 的 agent 都活在"一次进程调用"里：
> 跑 2 小时的任务崩溃在第 90 轮，一切归零。本 stage 将循环的进度**迁移到
> 磁盘**：每轮检查点、重启续跑、后台任务队列、取消传播——使长任务的存活
> 不再依附于进程。

## 1. 本阶段目标

**使长任务在进程终止后依然可续**：每轮循环落检查点（checkpoint），崩溃后
重启自动询问续跑；耗时的批量工作提交到异步任务队列（submit/poll），
不阻塞主对话；取消请求在"步边界"生效（cancel propagation）。

## 3. 原理与设计决策

**持久化执行的单位不是进程，是状态**（第 25 章）。传统脚本的结构性缺陷是
"状态在内存里"：进程终止即状态丢失。serverless 的结构性缺陷是"时间在
配额里"：15 分钟超时即任务终止。检查点 + 队列同时绕开这两个缺陷：
**状态在磁盘，执行在后台，进程仅承担承载职能，可随时终止与替换。**

**组件一：检查点（`checkpoint.py`）**
- 每轮循环结束 `save_checkpoint(history, task, turn)`——历史（append-only
  的消息列表）就是全部状态，序列化即存盘，无需事务设计；
- **原子写**：先写 `.tmp` 再 replace——防止写一半崩溃留下残缺检查点
  （残缺的检查点比没有更危险：恢复出一条坏历史）；
- 正常跑完自动清除；异常退出保留，重启时询问"续跑还是丢弃"。

**组件二：异步任务队列（`queue_manager.py`）**
- `submit` 立即返回 job_id，执行在 daemon 线程；主对话不被阻塞——
  这是"异步任务收敛粒度"（失败模式 #15 的对策之一）的最小实现；
- 每步之间检查取消标志：**取消传播不打断当前步，在下一步边界生效**——
  与分布式系统的取消语义一致（处于中间状态的写入不应被强行终止）；
- 完成/取消都把结果写 `jobs/<id>.md`（完成回调的模拟）：轮询方凭
  文件存在 + 状态行发现终态。本实现的"步"是 sleep(2) 模拟——
  真实系统里这一步是一次 LLM 调用或一段真实处理。

**组件三：取消传播的 agent 侧**：`submit_job` / `poll_jobs` / `cancel_job`
三个工具使 agent 自身也采用"提交-轮询"模式——长任务外包后台，主对话
保持畅通。

## 4. 运行方式

```bash
cd loop-engineering/stage09_long_running
pip install -r requirements.txt
# 填仓库根目录 config.py 三行后：
python src/main.py
```

崩溃恢复演示：

```
你> 读 store_a.csv，总结后写入 summary.md，再检查 workspace 文件数
│ [轮 1/15] 🔧 read_file
│ [轮 2/15] 🔧 write_file        ← 每轮都在落检查点
│ ^C（此时强行 Ctrl+C）
$ python src/main.py
🔍 发现未完成任务的检查点：
   任务：读 store_a.csv，总结后写入 summary.md……
   中断于：第 2 轮（2026-09-11T22:40:11）
   续跑该任务？(y=续跑 / 其他=丢弃检查点从头开始) > y
♻️ 已恢复检查点：任务「……」（中断在第 2 轮）
┌─ 续跑任务：……
│ [轮 3/15] 🔧 list_dir          ← 从第 3 轮继续，历史完整
└─ ✅ Final Answer: ……
```

异步队列演示：

```
你> 提交一个 8 步的批量分析任务
│ [轮 1] 🔧 submit_job(...) → 已提交异步任务 job-001（8 步，后台执行）
└─ ✅ 已提交，稍后可用 poll_jobs 查询。
你> /jobs
  job-001 [running] 3/8 —— 批量分析任务
你> /cancel job-001
  已请求取消 job-001（当前步完成后生效）
你> /jobs
  job-001 [cancelled] 4/8 —— 批量分析任务
```

完整示例见 `examples/transcript.md`。

## 5. 观察点

- **续跑的第一轮**：恢复后模型的行为是否连贯？它看到的是完整历史——
  连贯性取决于"历史即状态"这一设计的完整性。
- **检查点的时间戳**：/checkpoint 查看时间——每轮一存，丢失窗口是"当前
  一轮"而非"整个任务"。
- **取消的滞后性**：cancel 后当前步仍在执行（2 秒），下一步才停止——
  对比"协作式取消"与"强制终止"的差异（后者会留下不一致的中间状态）。
- **队列的结果文件**：jobs/job-001.md 中可以看到每步的流水——异步任务的
  "回调"在这里退化为文件，真实系统是 webhook / 消息队列。
- **进程身份的消失**：整个机制里没有任何对"当前进程"的依赖——这正是
  serverless / 服务化的理论基础。

## 6. 设计权衡

| 优势 | 代价 |
|---|---|
| 崩溃恢复把"丢一切"变成"丢一轮" | 每轮一次磁盘写（长历史时序列化有开销） |
| 异步队列让对话与长任务并行 | 单机线程实现，无持久化队列（重启丢后台任务） |
| 取消在步边界生效，状态不撕裂 | 协作式取消对"单步内部卡死"无能为力（需超时兜底） |
| 历史即状态：检查点零设计成本 | 跨机器恢复需要共享存储（本实现是本地文件） |

## 7. 同期竞争方案的淘汰原因

- **同步阻塞脚本**（跑完才返回）：AutoGPT 时代的默认形态。任务越长，
  崩溃期望损失越大——2 小时任务平均"终止于 1 小时处"，期望损失 50%。
  检查点把这一损失压缩到"一轮"。
- **serverless 直接部署**（单函数跑全程）：无状态部署很省心，但 15 分钟
  超时对长任务不可接受，且按运行时长计费对"等待 IO"极度不友好。
  正确做法是将长任务拆为带检查点的多段执行（或状态外置的队列消费）。
- **多进程守护 / 自动重启脚本**：crash-only 思路的朴素版——崩溃后重启
  整个任务。没有检查点，重启即重复消耗全部成本。crash-only 的正确形态
  正是"崩溃 + 检查点恢复"：崩溃本身并非问题，无法恢复才是。
