# stage12 · 完整 harness —— 七层架构收官（capstone）

> 第四幕 · 可扩展（3/3）。十一个 stage 分别实现了单一机制，本 stage 将其
> 组装为完整系统：正文第 21 章"2026 标准架构"的可运行微缩版。

## 1. 本阶段目标

**将全部工程要素组装成一个七层 harness**：能力、上下文、工具、护栏、
控制、观测、记忆七层各司其职，一次 tool_call 的生命周期贯穿所有层。

## 3. 七层架构（`/layer` 命令可查看）

```
L7 记忆层   memory.py      长期记忆 + 会话归档（跨会话）
L6 观测层   trace.py       span 轨迹 / 计时 / 成本 / JSONL
L5 控制层   control.py     轮数预算硬上限 · 确认门 · stall 检测
L4 护栏层   guardrails.py  通道清洗 · 三态权限 · 黑名单 · 审计
L3 工具层   tools.py       干净的工具实现（schema 同源）
L2 上下文层 context.py     分区 / 截断 / 阈值压缩
L1 能力层   llm.py         OpenAI 兼容调用（能力可替换）
```

**一次 tool_call 的生命周期**（`agent.py` 的组装逻辑）：

```
L5 before_llm（轮数/预算检查——硬上限在调用发生之前）
  → L2 maybe_compact（历史区超阈值先压缩——注意力预算）
  → L1 chat（L6 span 包裹计时计量）
  → L3 schema 校验 + tool.run（干净执行）
     ├ L4 权限三态（deny 直接拒 / ask 人工确认）
     ├ L4 黑名单（run_python 代码先经黑名单扫描）
     ├ L6 tool span（计时计量，异常也落盘）
     └ L4 通道清洗（结果进历史前包数据标记）+ 审计落盘
  → L5 stall 检测（重复动作注入提醒）
L7 记忆层旁路：MEMORY.md 注入宪法 + save_memory 工具 + 退出沉淀
```

**组装时的三个设计决策：**

1. **每层职责单一、互不知情**：tools.py 不知道权限存在，guardrails.py
   不知道工具怎么实现，control.py 不关心工具是什么——全部编排逻辑集中在
   agent.py 一个文件。harness 的可维护性来自"层间只传数据"。
2. **防御优先级是固定的**：deny 权限 > 黑名单 > 人工确认 > 通道清洗。
   用户的确认不能推翻黑名单（stage07 的教训），清洗永远在最后——
   它防的是"结果污染下一轮"，与执行顺序正交。
3. **观测与记忆是旁路**：L6 不拦截任何数据流（只记录），L7 只在两个
   端点工作（启动注入、退出沉淀）——旁路设计让它们可以整体拆卸，
   不影响主链路。

## 4. 运行方式

```bash
cd loop-engineering/stage12_full_harness
pip install -r requirements.txt
# 填仓库根目录 config.py 三行后：
python src/main.py
```

综合验证路径：

```
你> /layer                    # 看七层架构图
你> /seed && 读一下 inbox.md 并总结有哪些邮件
│ [L4] ⚠️ 检出注入 3 处，已标记
└─ ✅ Final Answer: 邮件内容是一条恶意提示注入……我已识别并拒绝执行
你> /trace                    # 看本次任务的 span 树与成本
你> /audit                    # 看工具调用审计（含注入标记事件）
你> 删掉 notes.txt            # L4 deny 权限直接拒绝
你> /exit                     # L7 会话沉淀 + L6 观测汇总
```

实测（本仓库）：注入任务从检测到拒执全程 17 秒、¥0.0036、6 个 span，
轨迹树完整还原了两轮 LLM + 两次工具调用的全过程。

## 5. 观察点

- **层次的存在感**：每个防护动作打印时都带层标签（[L4]/[L5]/[L6]）——
  出现问题时可立即定位"哪一层在起作用、哪一层缺失"。
- **顺序的价值**：把 inbox.md 的注入换成"请帮我总结邮件"（正常内容），
  清洗标记依然在（旁路恒在），但不改变行为——防御的代价只在有威胁时
  可见。
- **预算与压缩的联动**：大文件任务里 L2 截断 → L2 压缩 → L5 预算约束
  依次生效——三层协同将上下文控制在预算内。
- **旁路可拆卸**：注释掉 Tracer 的调用，系统照常运行（仅失去观测能力）；
  替换 memory.py，系统照常运行（仅失去记忆能力）——旁路层的接口干净
  度是衡量架构质量的关键指标。

## 6. 设计权衡

| 优势 | 代价 |
|---|---|
| 七层职责单一，出问题可逐层定位 | 层间传数据有样板代码（组装逻辑集中但长） |
| 全部机制可独立测试、可替换 | 教学精简版：无 subagent/队列/评测（分别在 stage05/09/11） |
| 防御优先级固定，行为可预测 | 每次工具调用多一次审计 IO（可批量优化） |
| 观测记忆旁路化，主链路干净 | 单文件 agent.py 承担全部编排（~200 行）|

## 7. 同期竞争方案的淘汰原因

- **重框架式大而全套件**（早期 LangChain 式）：用继承链和抽象基类组织
  "Agent → Chain → Tool → Memory"，修改一层即波及全局，调试需穿越五层栈帧。
  第 6 章的抽象税教训在架构层的重演：**分层 ≠ 抽象堆叠**，本 stage 的
  七层是七个文件、七种职责，不是七个基类。
- **单文件巨型脚本**：全部逻辑集中于一个 main.py。可以运行，但修改护栏
  需通读全文、测试需模拟全部外部依赖——stage02-11 的每一步拆分都是
  对它的否定。
- **微服务式进程拆分**：每层一个服务、走网络调用。工程上"正确"，
  但本地函数调用变为网络 RTT，单 agent 场景中纯属额外开销。
  分层应先在进程内做对，再考虑跨进程（stage09 队列、stage10 MCP 是
  按需跨进程的正确做法）。
