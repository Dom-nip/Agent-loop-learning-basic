# stage06 · 循环控制 —— 有界、可停、可干预

> 第二幕 · 可控（3/3）。前五个 stage 的循环停止依赖唯一硬性闸门 max_turns。
> 本 stage 将循环控制实现为显式机制：硬上限、人工确认门、stall 检测、短计划
> 重写。**控制不是事后补救，而是循环的内建器官。**

## 1. 本阶段目标

**将 AutoGPT 的三大失败根源逐项转化为机制**：无界循环 → 硬上限（轮数 +
token 预算）；无人干预 → 危险操作确认门；原地循环 → stall 检测 + 短计划重写。

## 3. 原理与设计决策

**四道机制的分工（`control.py`）：**

1. **硬上限（①）**：`before_llm()` 在每轮调用前检查——轮数超限或上下文规模
   超 token 预算即停，返回结构化 stop_reason。关键位置：检查在**调用前**，
   高成本调用不会发生。预算用估算值（stage03 的 tokens.py）做粗粒度刹车。
2. **确认门（②）**：工具带 `dangerous` 标记，执行前交互确认（y/n）。拒绝后
   **把"用户拒绝"作为工具结果喂回模型**——它获知被拒后会改道或解释，而非
   持续无效重试。这是 human-in-the-loop 的最小正确形态：不是砍掉能力，
   而是为能力加一道显式关卡。
3. **stall 检测（③）**：记录每轮动作签名 `(tool, args)`。连续重复 1 次 →
   注入提醒（nudge）；连续重复 2 次 → 强制计划重写（rewrite）。检测的
   假设：**同样的输入不会有新输出**——重复动作是循环失去信息增量的信号。
4. **短计划（④）**：任务开始先立 ≤5 步计划（一次独立调用），注入历史；
   stall 持续发生时，要求"结合已获得的观察"重写。计划是**消耗品**——
   长计划不随现实修订是 AutoGPT 的核心症结（失败模式 #13），短计划配合高频
   修订才是可行解。

**为什么这些控制要放在 harness 而不是 prompt？** stage05 结尾已经演示过：
"只分派 ≥2 个子任务"这类纪律写在 system prompt 里，模型照样违反——prompt
约束是软约束。轮数、预算、危险确认都是**代码可达的硬事实**，就应当用代码
执行（第 21 章："框架只用于约束层"的微缩版）。

```
你> 删掉 workspace 里的 notes.txt
│ [轮 3/12 · 预算≈4210/30000] 🔧 delete_file({'path': 'notes.txt'})

   参数：{'path': 'notes.txt'}
   允许执行？(y=允许 / 其他=拒绝) > n
│     → 用户拒绝执行此危险操作……
└─ ✅ Final Answer: 好的，我已放弃删除。这个文件是……

你> 读取 secret.txt 并总结
│ [轮 1] 🔧 read_file({'path': 'secret.txt'}) → 错误：文件不存在

│ ...
```

## 5. 观察点

- **确认门的两侧**：拒绝后模型是改道（转而询问用户原因）还是强行继续？
  以 `/gate off` 对照无确认门时的行为差异，检验"门"的实际作用。
- **stall 提醒的时机**：注入提醒后，模型首先道歉还是立即更换方法？能力
  较强的模型收到 nudge 后会先 `list_dir` 收集信息再行动。
- **预算停止的姿态**：`/budget 2500` 用于大任务，观察停止消息是否清晰
  说明"为什么停、做到哪了"——工程上停止必须可解释。
- **计划重写的质量**：重写后的计划是否真的吸收了"此路不通"的观察？
  （对照失败模式 #13：长计划不随现实修订。）
- **两个上限谁先到**：轮数上限抑制"空转"，预算上限抑制"冗长输出"——
  可观察常见任务更易受哪一类约束。

## 6. 设计权衡

| 优势 | 代价 |
|---|---|
| 保证停止：预算/轮数是硬数学，不靠模型自觉 | 预算估算是粗粒度的（±30%），阈值要留余量 |
| 危险操作有人工兜底，信任度可维持 | 确认门高频触发会引发确认疲劳，无差别确认反而构成风险 |
| stall 检测把空转消除在 2-3 轮内 | 签名级检测识别不了"语义重复"（以不同参数重复同一无效操作） |
| 短计划便宜（一次小调用）且灵活 | 计划与执行可能脱节（模型不回看计划） |

## 7. 同期竞争方案的淘汰原因

- **无界循环 + 被动等待**（AutoGPT 默认姿态）：官方配方的"Continuous Mode"。
  失败形态贯穿始终——成本失控、文件误写、长时间空转。教训凝练为一条
  铁律：**上线的 agent 循环必须有代码可达的停止条件**。
- **完全固定流程**（放弃自主性）：把任务写死成 if-else 流水线来"根治"失控。
  可靠性提升，但那已经是 workflow 而非 agent（第 9 章判据）——开放性任务
  无法套进固定流程。
- **让模型自己报告进度/自省停止**（"你觉得该停就停"）：纯 prompt 约束的
  典型失败——模型在长循环里会忘记承诺、或为了"完成任务"虚构进展。
  自省机制可以保留（STILL_NUDGE 即为其出口），但硬上限必须由代码实现。
