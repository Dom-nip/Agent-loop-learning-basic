# stage04 · 记忆与文件系统 —— 跨会话的三层记忆

> 第二幕 · 可控（1/3）。stage03 把上下文管住了，但**会话一关进程，一切归零**。
> 本 stage 将记忆外置到文件系统：跨会话的 MEMORY.md、逐会话的归档、agent 自行
> 维护的工作笔记——"文件系统就是 agent 的外置记忆"（Claude Code 的核心设计之一）。

## 1. 本阶段目标

**使 agent 具备跨会话的记忆**：三层记忆各司其职——会话历史（窗口内）、工作笔记
（notes/，任务中间状态）、长期记忆（memory/MEMORY.md + sessions/ 归档）。
新会话启动时注入记忆，会话结束前自动沉淀。

## 3. 原理与设计决策

**为什么是文件系统而不是向量数据库？** 记忆的核心矛盾不是"找不找得到"
（那是知识检索/RAG 的问题），而是"状态放哪里"：
- 文件路径是**确定性寻址**——`memory/MEMORY.md` 永远在同一个地方，"知道
  状态在哪"始终比"猜测哪里相关"可靠；
- Markdown 是**人机共读**的——可直接编辑、diff、纳入 git；
- AutoGPT 式"向量库存一切"的后果是时序错乱、新旧混杂、召回大量弱相关
  文本（第 4 章的历史遗留影响，见附录 B 失败模式 #10）。**语义检索管知识，路径寻址管状态**。

**本 stage 的关键实现决策：**

1. **启动注入**（`agent.py` 的 `_system_prompt`）：MEMORY.md 全文 + 最近一份
   会话摘要拼进 system prompt。记忆进的是"宪法层"，不是历史层——它是背景
   约束，不是对话。
2. **收尾沉淀**（`memory.py` 的 `distill_session`，由 `/exit` 触发）：
   - 一步：LLM 把整个会话压缩成归档摘要 → `sessions/<时间戳>.md`；
   - 二步：LLM 从会话里筛"值得跨会话记住的长期事实"（偏好/约束/决定），
     输出 JSON 数组 → 追加进 MEMORY.md（带日期戳）。
   沉淀失败不阻塞退出——记忆是增益，不是关键路径。
3. **显式记忆工具**（`save_memory` / `recall_memory`）：让模型在会话中途就能
   存档关键事实，而不必等到收尾。工具的 description 明确写了"临时状态不要
   存这里"——分层纪律靠接口文档约束模型行为。
4. **工作笔记层**：不设专门工具，就是 read/write/list 操作 `notes/`。
   中间状态本来就是文件，agent 自行管理即可——这是"文件系统即上下文"
   的直接体现。
5. **遗忘机制**：`/forget` 清空 MEMORY.md（归档保留）。缺乏遗忘机制的记忆
   将无限膨胀并稀释检索价值（第 13 章的记忆检索账本）。

## 4. 运行方式

```bash
cd loop-engineering/stage04_memory_filesystem
pip install -r requirements.txt
# 填仓库根目录 config.py 三行后：
python src/main.py
```

跨会话演示路径：

```
# 会话 1
你> 记住：我在做电商后台项目，偏好 Python，团队规定不用 Docker
│ [turn 1] 🔧 save_memory({"fact": "用户在做电商后台项目；偏好 Python；团队规定不用 Docker"})
你> /exit
🧹 会话收尾：正在沉淀记忆……
   📄 会话摘要已归档：20260911-213045.md
   🧠 新增长期记忆 1 条

# 会话 2（重新运行 python src/main.py）
✅ 已加载长期记忆（XXX 字符）+ 1 份历史会话归档。
你> 我们上次聊到哪了？我的项目用什么语言？
```

## 5. 观察点

- **第二次启动的第一句话**：模型是先复述记忆再工作，还是自然地带着记忆
  工作？好的记忆注入表现为"背景"，而非"开场白素材"。
- **save_memory 的触发时机**：明确说"记住 X"它一定调用；随口提一句偏好，
  它会调用吗？（主动记忆是行为分水岭——能力较强的模型会主动调用，较弱
  的模型需要明示。）
- **沉淀筛选的质量**：`/exit` 时检查筛出了什么。临时任务细节混进 MEMORY.md？
  说明 MEMORY_PROMPT 的边界约束需要收紧——记忆筛选器本身要迭代。
- **记忆冲突**：连续两次说"记住：我偏好 X"和"我不再偏好 X"，观察 MEMORY.md
  中出现的矛盾条目——**追加式记忆没有冲突消解**，这是本方案最主要的缺陷
  （stage12 的完整 harness 实现了合并去重）。

## 6. 设计权衡

| 优势 | 代价 |
|---|---|
| 确定性寻址：记忆永远在固定路径，无检索失败 | 没有语义检索：记忆多了只能全文注入或人工整理 |
| 人机共读共写：可编辑、可 diff、可 git | 追加式写入无冲突消解，矛盾条目会累积 |
| 零基础设施：两个 md 文件夹就是记忆库 | 单文件注入撑不住大规模记忆（记忆量需上限管理） |
| 沉淀/筛选逻辑完全透明可调 | 每次退出多花 2 次 LLM 调用 |

## 7. 同期竞争方案的淘汰原因

- **纯向量记忆库（AutoGPT 式方案）**：把任务状态、用户偏好、对话片段全部
  embedding 进向量库，检索时按相似度召回。失败原因有三：时序错乱（旧状态
  重新浮现）、确定性丧失（"此前交代的事项"竟需依靠相似度猜测）、不可审计
  （出错后无从追溯记忆内容）。向量检索的正确位置是**知识召回**
  （RAG），不是状态管理。
- **无记忆每次从零**：依赖用户每次重新自我介绍。对一次性问答尚可成立，
  对长期协作型 agent（编程助手、项目管理）则不可接受。
- **数据库/专有记忆服务**（Mem0、Zep 等托管方案）：能力更强（时序、冲突
  消解、自动遗忘），但引入基础设施依赖。教学 stage 用文件系统讲清原理，
  生产需求复杂后自然升级——**文件系统是记忆的最简可行方案，不是反方案**。
